# Playwright Python POM Framework

A small, maintainable UI automation starter framework built with Python, Pytest, Playwright, and Page Object Model.

## Project layout

- `pages/`: reusable page objects and shared browser actions.
- `tests/ui/`: test cases; product assertions and test flow stay here.
- `utils/`: YAML and environment configuration plus logging.
- `test_data/`: non-secret JSON data used by tests.
- `config/`: safe project defaults.
- `reports/`: framework logs and generated report artifacts.
- `reports/html/`: generated pytest HTML reports.
- `reports/allure-results/`: raw Allure result files generated by pytest.
- `reports/allure-report/`: generated Allure HTML report.
- `screenshots/`: screenshots captured when a test fails.
- `traces/`: Playwright traces captured when a test fails.

`pages/login_page.py` contains clearly marked sample locators. Replace them with locators from the application under test before writing real login coverage.

## Installation

From the `playwright_python_pom` directory:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m playwright install
```

Reporting dependencies included in `requirements.txt` are `pytest-html` and `allure-pytest`.

Install only selected browser engines when appropriate:

```powershell
python -m playwright install chromium firefox webkit
```

## Configuration

Defaults are in `config/config.yaml`. Environment variables override them:

- `BASE_URL`: application base URL.
- `TIMEOUT`: default Playwright timeout in milliseconds.
- `BROWSER_NAME`: supported by the config reader for custom settings.

Keep credentials outside source control. `.env` is ignored by Git and is provided only as a template.

Create a local `.env` file in the project root with the centralized OrangeHRM settings:

```dotenv
ORANGEHRM_URL=https://opensource-demo.orangehrmlive.com/
ORANGEHRM_USERNAME=Admin
ORANGEHRM_PASSWORD=admin123
```

These values are loaded by `config/settings.py`. Tests should use the reusable `logged_in_page` fixture for flows that begin after authentication:

```python
def test_admin_user_search(logged_in_page, user_data):
    admin_page = AdminPage(logged_in_page)
```

The fixture opens the configured URL, logs in through `LoginPage`, verifies the Dashboard, and reuses the existing `page` fixture for browser cleanup, screenshots, traces, and report attachments. Passwords are never added to reporting metadata or terminal output.

For tests that can reuse a session without performing UI login, request the opt-in `authenticated_page` fixture. It creates a fresh context from a worker-safe `storage_state` generated by the `auth_state` fixture:

```python
def test_authenticated_area(authenticated_page):
    DashboardPage(authenticated_page).expect_loaded()
```

The existing `logged_in_page` fixture remains available for tests that specifically cover the login flow. Authentication state is stored at `auth/storage_state.json`, ignored by Git, and never attached to reports.

Refresh the state explicitly when credentials or the server session changes:

```powershell
python -m pytest tests/ui/test_pim.py::test_admin_can_delete_employee_from_pim -v --pom-refresh-auth
```

The same command generates the state if it is missing. Without `--pom-refresh-auth`, the fixture validates the saved state and refreshes it automatically when the Dashboard is no longer reachable.

API tests can request the `api_request_context` fixture. It creates a fresh Playwright `APIRequestContext` using the same configured base URL and disposes it after the test:

```python
from api.base_api_client import BaseApiClient


def test_health_endpoint(api_request_context):
    response = BaseApiClient(api_request_context).get("/health")
    BaseApiClient.assert_status(response)
```

Create endpoint-specific clients under `api/` rather than putting API calls directly in tests. The fixture is independent from browser contexts, so it can also be combined with `authenticated_page` for hybrid workflows.

Authenticated API tests use `authenticated_api_request_context` or the `employee_api` fixture. The API context loads the same ignored `auth/storage_state.json` used by the browser. API-created employees use unique IDs and are deleted in `finally` blocks. Run API and hybrid coverage with `python -m pytest tests/api -m "api or hybrid" -v`; destructive tests can be included explicitly with `-m "api or hybrid"`.

UI network tests can use `mock_route` to fulfill, continue, or abort matching requests. Fulfilled routes support JSON bodies, status codes, headers, and delay simulation. Use `BasePage.wait_for_response` around the action that triggers a request so the response assertion is synchronized with Playwright's event model.

CI and quality entry points are included in `.github/workflows/playwright.yml`, `Jenkinsfile`, `Dockerfile`, and `pyproject.toml`. The primary workflow runs smoke/sanity coverage on pull requests, selected suites on pushes to `main`/`develop`, and regression coverage nightly. It supports manual environment (`qa`, `uat`, `staging`) and suite selection. URLs and credentials come from GitHub environment secrets or Jenkins credentials; no secret values are stored in the repository. BDD, accessibility, and visual testing remain optional extensions: use the registered `hybrid`, `accessibility`, and `visual` markers and add their tool dependencies only when the product needs those contracts.

## Running tests

Tests are categorized with `smoke`, `sanity`, `regression`, `ui`, `api`, `e2e`, `login`, `pim`, `critical`, `negative`, and `integration` markers. Examples:

```powershell
python -m pytest -m smoke
python -m pytest -m api
python -m pytest -m regression
python -m pytest -m "smoke or sanity"
python -m pytest -m "not regression"
```

Run independent coverage in parallel with xdist. Use the workspace virtual environment when the global Python interpreter does not contain the project dependencies:

```powershell
python -m pytest -n auto -m "smoke or sanity"
```

Tests use function-scoped browser contexts/pages, unique API data, and node-specific artifact names. Destructive tests are explicitly marked so they can be excluded or scheduled separately.

The CI-equivalent commands are:

```powershell
# Pull request smoke gate
python -m pytest -n auto -m "smoke or sanity" --reruns 1 --only-rerun "TimeoutError|net::ERR|TargetClosedError" --pom-video on --html=reports/html/report.html --self-contained-html --junitxml=reports/junit.xml --alluredir=reports/allure-results --clean-alluredir

# API suite
python -m pytest -n auto -m api --pom-video on --junitxml=reports/junit.xml --alluredir=reports/allure-results

# UI suite
python -m pytest -n auto -m ui --pom-video on --html=reports/html/report.html --self-contained-html --junitxml=reports/junit.xml --alluredir=reports/allure-results

# Regression suite
python -m pytest -n auto -m regression --pom-video on --html=reports/html/report.html --self-contained-html --junitxml=reports/junit.xml --alluredir=reports/allure-results
```

Run the Docker equivalent with `docker build -t playwright-python-pom .` followed by `docker run --rm --shm-size=2g --env-file .env -e ENVIRONMENT=qa playwright-python-pom -n auto -m "smoke or sanity"`. Mount `reports`, `screenshots`, `traces`, and `videos` when artifacts must be retained outside the container.

For Jenkins, configure `ORANGEHRM_URL`, `ORANGEHRM_USERNAME`, `ORANGEHRM_PASSWORD`, and `BASE_URL` as credential-bound environment variables, then run `python -m pytest -n auto -m "${TEST_MARKER:-regression}" --pom-video on --html=reports/html/report.html --self-contained-html --junitxml=reports/junit.xml --alluredir=reports/allure-results`. The existing [Jenkinsfile](Jenkinsfile) archives reports and failure evidence.

Run the demo test headlessly in Chromium:

```powershell
python -m pytest -q
```

Choose another browser:

```powershell
python -m pytest -q --pom-browser firefox
python -m pytest -q --pom-browser webkit
```

Run headed:

```powershell
python -m pytest -q --pom-headed
```

Override the target URL and tracing:

```powershell
python -m pytest -q --pom-base-url https://example.com --pom-tracing off
```

The login test targets the OrangeHRM demo application configured in `.env`. Admin search values are loaded from `test_data/users.json`; keep real credentials outside source control.

## Reports

Generated output is kept in these locations:

- `reports/html/report.html`: self-contained pytest-html report with status, duration, environment, and failure artifacts.
- `reports/allure-results/`: raw Allure results with title, description, feature, story, severity, steps, parameters, and attachments.
- `reports/allure-report/`: generated Allure HTML report.
- `screenshots/`: failure screenshots.
- `traces/`: Playwright trace ZIP files for failed tests.
- `videos/`: opt-in failure videos.
- `reports/diagnostics/`: failure-only console and failed-request diagnostics.

Clean generated output before a fresh run (PowerShell):

```powershell
Remove-Item reports/html/*, reports/allure-results/*, reports/allure-report/*, screenshots/*, traces/* -Recurse -Force -ErrorAction SilentlyContinue
```

Generate the required HTML report and Allure results in one pytest run:

```powershell
python -m pytest -v --html=reports/html/report.html --self-contained-html
```

To generate both report formats together:

```powershell
python -m pytest -v --html=reports/html/report.html --self-contained-html `
    --alluredir=reports/allure-results --clean-alluredir
```

Open the self-contained HTML report directly from `reports/html/report.html`. It includes the dashboard totals and pass percentage, per-test status/module/browser/environment/time, captured steps and logs, failure tracebacks, screenshots, and Playwright trace links. Set `ENVIRONMENT` to label a run, for example `$env:ENVIRONMENT="staging"`.

Generate and open the Allure HTML report:

```powershell
Remove-Item reports/allure-report/* -Recurse -Force -ErrorAction SilentlyContinue
allure generate reports/allure-results -o reports/allure-report
allure open reports/allure-report
```

The Allure commands require the separate Allure command-line tool. If `allure` is not recognized, install Allure Report and its Java prerequisite, then reopen the terminal before running those commands. The Python adapter generates `reports/allure-results`; the CLI generates `reports/allure-report`.

Open the generated Allure report with:

```powershell
allure open reports/allure-report
```

The framework uses its existing custom Playwright fixtures and remains compatible with pytest and Playwright. Passwords are masked in terminal output and are not added as report parameters. Keep real credentials outside source control; Playwright traces can contain page data and should be treated as sensitive artifacts.

For failure diagnostics, tracing remains enabled by default. Video recording is opt-in with `--pom-video on`; videos, traces, screenshots, and console/request diagnostics are attached to Allure and pytest HTML reports when available. Parallel runs can use `python -m pytest -n auto`; worker-specific storage-state names prevent authentication collisions.

## Interactive test runner

The project root contains `run_tests.ps1`, an interactive menu for the common pytest and reporting commands:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\run_tests.ps1
```

Select an option from the menu:

1. Run all tests with `python -m pytest -v`.
2. Run all tests headed with `python -m pytest -v --headed`.
3. Run the headed OrangeHRM login test.
4. Run the login test with Allure results.
5. Generate `reports/allure-report` with the Allure CLI.
6. Open the generated Allure report.
7. Generate `reports/html/report.html` with pytest-html.
8. Run the login test and generate both pytest-html and Allure results.
9. Exit.

The script reports clear errors when `python`/pytest or the `allure` command-line tool is unavailable. Install project dependencies and Playwright browsers before using the menu:

```powershell
python -m pip install -r requirements.txt
python -m playwright install
```

The Allure generation and open options require the separate Allure Commandline tool and Java. The script runs from the project root, so all existing report paths remain unchanged.
